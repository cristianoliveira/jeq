# Smart grep: retrieve locally, judge a shortlist

Use JEQ to prioritize log excerpts against a question, without sending the whole
log or making one request per line. This is a retrieval-and-ranking recipe, not
an exhaustive semantic grep or a root-cause detector.

```text
local log → explicit regex + short context → exact deduplication
          → review bounded JSON → one jeq rank request → evidence + line references
```

## Run the example

Requires Python 3, Bash, `jeq`, and `jq`. Run from the repository root. The first
step is offline; the second sends reviewed excerpts to TypeSafe and spends API
budget. No live call is part of the automated tests.

### 1. Prepare and inspect candidates locally

```sh
mkdir -p .tmp/smart-grep
python3 examples/smart-grep/prepare.py \
  examples/smart-grep/fixtures/toon-tests.txt \
  '^        --- FAIL:' \
  > .tmp/smart-grep/candidates.json

jq . .tmp/smart-grep/candidates.json
```

The regex selects leaf test failures instead of their parent summaries. By
default, each excerpt includes the matching line and **one following line**.
That following line matters: a test named `throws_on_blank_line` describes the
expected behavior, while `expected decode error, got ...` describes the failure.

Only identical complete excerpts are grouped. `lines` retains every matching
line number in the source file; `id` uses the first occurrence. IDs, timestamps,
status codes, and other potentially meaningful fields are not normalized.
The input file path is not included in the candidates.

Preparation fails rather than silently sampling when it exceeds:

- 1 MiB of input;
- 30 distinct excerpts, plus one `none` candidate;
- 12 KiB of candidate JSON, including line references.

`--context 0`, `1`, `2`, or `3` controls following lines. It does not reconstruct
multiline events or stack traces. No matches exits 1; invalid input or a budget
violation exits 2. Failures write no partial JSON to stdout.

These caps apply to preparation, not arbitrary JSON supplied directly to
`rank.sh`. The regex is local Python syntax chosen by the caller, never generated
or executed from model output.

### 2. Make one explicit live request

After reviewing the payload and setting `TYPESAFE_API_KEY`:

```sh
bash examples/smart-grep/rank.sh \
  'Find failures where invalid blank lines were accepted instead of rejected.' \
  < .tmp/smart-grep/candidates.json \
  > .tmp/smart-grep/ranked.json

jq '.items[:5] | map({
  id, probability,
  lines: .candidate.lines,
  excerpt: .candidate.description
})' .tmp/smart-grep/ranked.json
```

The script is a thin wrapper around `jeq rank`. It accepts exactly one query,
reads reviewed JSON on stdin, and disables retries so the experiment attempts
at most one API request. `JEQ_BIN` can select a local binary. Normal JEQ model
configuration and `TYPESAFE_BASE_URL` still apply.

The complete result retains `_jeq.relevance`, including the resolved model and
usage. Ranking keeps the original candidates, so displayed text and source line
numbers are copied from local data, not generated by the model. Keep the source
file unchanged while using its line references.

**Choice probabilities are relative.** They are not independent relevance scores,
and top-five is only a display choice. Several useful excerpts compete for the
same probability mass. Keep `none` visible: if it ranks first, the model did not
find a better match. That is not proof that the original log lacks evidence.
Do not interpret a low-ranked excerpt as irrelevant or turn these numbers into
an automatic production threshold.

## Try another log and a negative query

The build fixture contains environment warnings, two actionable lint diagnostics,
and final `make` failure messages:

```sh
python3 examples/smart-grep/prepare.py \
  examples/smart-grep/fixtures/build-check.txt \
  'warning:|unused-parameter:|Error [0-9]' \
  > .tmp/smart-grep/build-candidates.json

# Inspect before sending.
jq . .tmp/smart-grep/build-candidates.json
bash examples/smart-grep/rank.sh \
  'Which diagnostic identifies a code issue that must be fixed for this check to pass, rather than an environment warning or a final make failure?' \
  < .tmp/smart-grep/build-candidates.json \
  > .tmp/smart-grep/build-ranked.json
```

For a no-match check, reuse the test shortlist with a question it cannot answer:

```sh
bash examples/smart-grep/rank.sh \
  'Find evidence of a database connection timeout.' \
  < .tmp/smart-grep/candidates.json \
  > .tmp/smart-grep/no-match-ranked.json
```

To compare context against names alone, prepare the test fixture again with
`--context 0` and run the same blank-line query. To observe exact deduplication
locally, prepare the build fixture with `--context 0`: its two identical dirty-tree
warnings collapse to one candidate with `lines: [1, 3]`.

## What the live experiment showed

Exploratory observations with resolved model `jev-1.13.0` on 2026-09-20. These are
individual observations, not expected test outputs or a calibrated benchmark.
The four rows below use the same committed ranking instruction:

| Input / query | Top result | Relative probability | Input / output tokens |
| --- | --- | ---: | ---: |
| Test names only / blank-line rejection | `none` | 0.45 | 1507 / 263 |
| Test names + one context line / same query | Blank-line rejection failure, line 101 | 0.76 | 2676 / 267 |
| Same contextual excerpts / database timeout | `none` | 1.00 | 2672 / 263 |
| Build excerpts / actionable diagnostic | Unused parameter, line 11 | 0.81 | 710 / 96 |

The second unused-parameter diagnostic ranked second in the build trial. The
first three results in the contextual blank-line trial were relevant failures.
Adding context corrected the top result in this small comparison; repeated runs
may differ. Two earlier exploratory calls used different instructions and are
not included in the table.

The test log is 121 lines / 10,750 bytes. Plain `FAIL` matching finds 32 headers;
local extraction produces 23 excerpts plus fallback, encoded in 8,158 bytes of
candidate JSON. Names alone use 4,109 bytes but performed worse. Candidate JSON
size is not wire size: JEQ constructs the API question from the descriptions.

The build log is only 1,008 bytes; its candidate JSON is **larger**, at 1,223
bytes. This example demonstrates useful prioritization, not universal bandwidth
savings. Exact grouping saves more when events genuinely repeat. Neither fixture
proves an advantage over a carefully chosen regex: they are small, understandable
smoke tests. Next evaluate recall and cost on a labeled, larger log.

## Safety and limitations

- Inspect and redact **before** the live step. The preparer is not a secret scrubber.
  Following context lines can contain credentials or personal data.
- Narrow large files locally by time, service, or an incident window. Preparation
  does not take the first N matches and silently discard the rest.
- Relevant events excluded by the regex cannot be recovered by ranking.
- Preserve evidence that distinguishes events. Do not aggressively merge logs
  just to reduce cost; one context line may still be insufficient.
- Treat log contents as untrusted data. Do not execute excerpts, model-selected
  IDs, or model output as shell commands or paths.
- A relative winner does not establish causality, absolute suitability, or that
  all matching events were found. For independent relevance judgments, consider
  `map` with a Noul question per group instead, with a different request budget.

## Fixture provenance and offline verification

`fixtures/toon-tests.txt` is a reviewed historical Go TOON fixture-test failure log
from this checkout. Its names and sample values belong to test fixtures, not
customer records. `fixtures/build-check.txt` is a historical local check log with
the workstation path and Nix derivation hash replaced and terminal colors removed.
Neither log describes the current health of the repository.

The Go examples suite tests exact grouping, context, line references, input and
payload limits, no-match and invalid-input paths, and the real JEQ CLI against a
local fake API. It checks request count, evidence preservation, and no retries
on API failure. It does not assert live model judgments.

```sh
go test ./examples -run '^TestSmartGrep'
```
